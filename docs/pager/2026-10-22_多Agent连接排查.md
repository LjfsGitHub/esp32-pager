# 2026-10-22 多 Agent 连接排查与自动登录

## 结论

Cursor、Codex、Claude、WorkBuddy 四个 ACP 适配器都能正常启动并完成 `initialize`。排查时这四个 Agent 在本机都还没有完成登录；本次处理中 Cursor 已完成登录并建立 session，其余三个仍待完成：

| Agent | 排查时状态 | 未登录时的表现 |
|---|---|---|
| Cursor | `Not logged in` | `session/new` 返回 `Authentication required` |
| Codex | `Not logged in` | `session/new` 返回 `Authentication required` |
| Claude | `loggedIn: false` | 会话能建立，但首个 prompt 返回 `Authentication required` |
| WorkBuddy | `hasSession=false hasAccessToken=false` | `session/new` 返回 `Authentication required` |

现在切换到一个未登录的 Agent 时，bridge 会**自动拉起对应的登录界面**，PC 页面和设备端会显示“等待登录”，不再只显示一条离线提示。认证仍然全部在 PC 上完成；设备只接收状态和对话，不接触任何 Agent 凭据。

## 自动登录流程

### Cursor / Codex / WorkBuddy（ACP `authenticate`）

1. 启动适配器，`initialize`，调用 `session/new`。
2. 如果返回认证错误，读取 `agents.json` 中的 `authMethod`。
3. 发送 ACP `authenticate`（`{ "methodId": ... }`），适配器打开浏览器登录页并在后台等待。
4. 用户完成浏览器/扫码登录后，`authenticate` 返回；bridge 重新调用 `session/new`。
5. 成功则进入 `IDLE`；失败或 300 秒超时则进入 `OFFLINE`，并显示对应登录提示。

当前方法 ID：

- Cursor：`cursor_login`
- Codex：`chat-gpt`
- WorkBuddy：`internal`（微信登录，与 `CODEBUDDY_INTERNET_ENVIRONMENT=internal` 一致）

如果 WorkBuddy 要改用 Google/GitHub 登录，把 `authMethod` 改成 `external`；企业域名用 `selfhosted`，iOA 用 `iOA`。修改后重启 bridge。

### Claude（可见 CLI 登录窗口）

Claude 的 ACP 适配器没有 `authenticate` 方法，而且 `claude auth login` 会输出 OAuth 链接后提示：

```text
Paste code here if prompted >
```

因此不能把它的 stdio 重定向到 bridge 日志，否则用户无法粘贴授权码。流程是：

1. `session/new` 成功后读取 `_auth/status_update`；`kind=none` 表示未登录。
2. 关闭这个已建立但不可用的会话。
3. 用 `Start-Process -WindowStyle Normal` 打开一个**可见的 Claude 控制台**，运行 `claude auth login`。
4. 每秒执行一次 `claude auth status`，最多等待 300 秒。
5. 登录成功后启动新的 ACP 客户端和会话，进入 `IDLE`。

Claude 登录命令和检查命令配置在 `agents.json`：

```json
"loginCommand": "%LOCALAPPDATA%\\pager-agents\\node_modules\\@anthropic-ai\\claude-agent-sdk-win32-x64\\claude.exe",
"loginArgs": ["auth", "login"],
"loginCheckArgs": ["auth", "status"]
```

## 配置字段

`agents.json` 新增以下可选字段：

| 字段 | 作用 |
|---|---|
| `authMethod` | ACP `authenticate` 的 methodId；没有该字段时不自动调用 ACP 登录 |
| `loginCommand` | CLI 登录程序；用于 Claude 这类没有 ACP 登录方法的适配器 |
| `loginArgs` | 传给 `loginCommand` 的参数 |
| `loginCheckArgs` | 登录状态检查参数；退出码 0 表示已登录 |

`loginArgs` / `loginCheckArgs` 必须和 `loginCommand` 一起出现，否则 profile 加载会报错。

## Cursor `Connection stalled` 定位（2026-10-22 下午）

登录不是问题：`cursor-agent status` 已显示登录，ACP `session/new` 正常。问题发生在 `session/prompt` 的 agent 流阶段。

直接绕过 bridge 运行：

```powershell
cursor-agent -p --trust --mode ask --output-format text "只回复 OK"
```

同样卡住/重连，说明不是 pager bridge、设备端或认证逻辑导致。Cursor ACP 在约 30 秒无入站帧后报 `RetriableError: Connection stalled`；这是 Cursor 客户端的 30 秒 watchdog，不是登录失效。

网络侧观察：

- Cursor 状态页当时全部 Operational。
- `api2.cursor.sh` 可连通（HTTP 200，TLS 1.3）。
- 实际 agent 流端点从重连日志看到是 `agentn.global.api5.cursor.sh`（AWS 新加坡）。
- 该域名解析到 `52.74.223.220` 和 `54.169.137.161`；其中 `54.169.137.161:443` TLS 握手超时，`52.74.223.220` 可完成 TLS。
- 当前 Windows 系统代理关闭，Clash 的 `127.0.0.1:7877` 没有监听；PC 是直连。
- 已试 `useHttp1ForAgent=true`（HTTP/1.1 兼容模式），仍卡住，已恢复为 `false`。
- 已试把 `agentn.global.api5.cursor.sh` 临时固定到可握手的 `52.74.223.220`，仍卡住，hosts 已恢复。

结论：认证正常，问题在 PC 到 Cursor agent 后端的流式连接/网络路径。Cursor 官方论坛对同类 30 秒 stall 的建议也是换网络、关闭/更换 VPN/代理、检查 HTTPS 扫描。

恢复顺序：

1. 用手机热点让 PC 联网，重试 Cursor prompt；若成功，说明当前宽带到新加坡 agent 节点的路径有问题。
2. 若必须用当前网络，启用 Clash 并确认 `127.0.0.1:7877` 在监听，然后在 Cursor profile 的 `env` 中加入 `HTTPS_PROXY` / `HTTP_PROXY`（只影响 Cursor），重启 Cursor profile 再测。
3. Cursor 恢复前先用 Hermes 继续工作；不要反复退出/重新登录 Cursor，登录状态没有丢失。
